## v0.1.9 下载与自动转换格式（核心，全栈）

反馈：**下载并自动转换格式**，候选库 [ncmdump](https://github.com/taurusxin/ncmdump)。技术不确定性最大的一版（跨语言依赖 + 后端新链路 + 版权边界 + 大文件 UX）。

- **先决问题**：目标场景是 (a) API 直链音频下载 + 统一转码、(b) 解密用户自备 `.ncm` 文件，还是 (c) 两者都要——结论直接决定集成路线。
- **集成路线候选**：后端 Python 流式下载 + `ffmpeg` 转码 / `ncmdump` CLI 或库（Windows 向，需评估跨平台替代）/ 前端 WASM 解密 + 浏览器下载（后端零改动、隐私最优）。
- **链路要点**：单曲流式下载接口（`?format=mp3|flac`）；歌单 / 专辑批量下载需任务队列 + 进度反馈（zip 打包）；VIP 音质「可播放 ≠ 可下载」的降级策略。
- **合规红线（先定死再开发）**：仅限用户有权收听的内容供个人离线使用，不做分享分发；README 加使用声明；整单批量下载默认关闭、设置中显式开启。
- **UX**：单曲右键「下载」+ 详情页批量入口；格式 / 音质默认值进设置；断点续传 v1 不做。

## v0.2.0 后端 SDK 迁移（架构版）

**后端 SDK 从 pymusiclibrary（Windows 原生库，崩溃/串行/平台限制）切换到 NeteaseCloudMusicApi（纯 Node.js）。** 设计已批准（方案 B：Node stdio worker），完整设计见 `V0.2.0_DESIGN.md`；**排期在 v0.1.x 完成之后启动**。

- **收益**：跨平台（解锁 Docker）、删整套子进程隔离、上游调用真并发、解锁「最近播放」云端版。
- **主体工作**：`core/` 接入层改造 + 隔离机制删除 + 22 个调用点迁移回归（≈ 3.5~5 人日）；services 层及以下不动。
- 2026-10 全库审查发现的「随迁移解决项 / 提前到 v0.1.x 项」归属表见 `V0.2.0_DESIGN.md` §7。

## 技术债待办（2026-09 一致性治理）

来源：代码风格一致性审计（A/B/C 清单）。低风险项已交付（分页批全局统一 `PAGE_SIZE=40`、AlbumPage 错误态对齐、全局 toast 抽出 `uiStore`、路由归位、续拉失败断链），以下结构项分步待做：

1. **B1 补拉编排对齐**：`_albums_state`（`backend/app/services/library_service.py`）仍是逐页 `while` 串行补拉，对齐 `_likes_state` 的缺口多页 `gather` 一次编排。
2. **B2 加载更多交互统一**：`LikePage`/`ShelfPage` 滚动无限加载，`SearchPage`/`ArtistPage` 用「加载更多」按钮——同类操作两种 UX，定一种。
3. **C3 queueSource 标签风格统一**：`歌单《X》`/`专辑《X》`/`歌手《X》` 用书名号，`我喜欢的音乐`/`自听榜`/`搜索结果`/`最近播放`/`单曲` 用裸名；可与 v0.1.8「队列右键查看来源」的 `queueSource` 结构化升级 `{ kind, id, name }` 一并做。（queueSource 结构化已随 v0.1.8 交付，见 `frontend/src/types/index.ts` QueueSource；标签风格统一仍待做）
4. **A7 接口 limit 上限策略**：`/user/likes`、`/user/albums` `le=200`；`/search`、`/artist/albums` `le=50`；`/user/record` `le=100`——属接口语义，动前先定统一策略。

## 非目标（红线）

1. 链接式 / 二维码分享（反馈已否决）。
2. 音频文件 / 歌单打包分发：版权红线，永久不做。
3. 大文件断点续传（v1 明确不做）。
