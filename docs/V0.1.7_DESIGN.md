## 1. 定位

一个主题：**封面的呈现与传播**。两项反馈合并成版——**唱片架展示（唱片墙）**与**分享（卡片式）**，同属封面视觉链路、共享渲染与导出组件，一次设计、一起交付。

## 2. 范围（思路）

1. **分享卡片**（单曲 / 专辑 / 歌单）：以**图片卡片**形式分享——非链接、**无二维码**；前端生成卡片图片，导出/发送方式待定。
2. **唱片墙**：`ShelfPage` 收藏专辑的展示升级（现为普通封面网格）；可延伸**唱片墙分享**（把唱片墙生成卡片）。视觉与交互方案待定。

## 3. 暂定原则

- 分享形态 = **图片卡片**：不做链接分享、不做二维码、不含音频文件。
- 倾向**纯前端实现**（canvas / DOM 渲染导出），后端预期零改动（数据源复用 `libraryApi.*` 现有接口）。
- 与现有 7 套主题色兼容。

## 4. 非目标

1. 下载与自动转换格式（→ v0.1.8，见 §9.2）。
2. 链接式分享（反馈已明确否决）。
3. 音频文件 / 歌单打包分发：版权红线，永久不做。

## 5. 待讨论清单（下一轮确定）

- **分享卡片**：版式与尺寸、卡片内容元素、导出/发送方式、入口位置、单曲/专辑/歌单的差异处理。
- **唱片墙**：视觉风格、交互方式、排序/筛选、大收藏量下的性能边界。
- **共享边界**：卡片渲染是否复用唱片墙视觉；两者的组件拆分。

### 9.2 v0.1.8 下载与自动转换格式（核心，全栈主题版）

反馈「**下载并自动转换格式：使用库 [ncmdump](https://github.com/taurusxin/ncmdump)**」。独立成版理由：跨语言依赖集成 + 后端新链路 + 版权合规边界 + 大文件/转码 UX，是本批**技术不确定性最大**的需求。

**预研要点（S0 级调研建议提前并行）**：

1. **场景澄清（先决问题）**：`ncmdump` 解的是网易云 `.ncm` 加密缓存；而 API 直链拿到的一般是普通 mp3/flac。需澄清目标场景：(a) 下载 API 直链音频 + 统一转码格式；(b) 解密用户自备 `.ncm` 文件；(c) 两者都要。**结论直接决定集成路线**。
2. **集成路线候选**：
   - 后端 Python 直连：下载流 → `ffmpeg` 转码（依赖本机 ffmpeg，启动时探测并提示）；
   - `ncmdump` 以 CLI/库形式集成（C++/C# 实现，Windows 向；需评估跨平台替代（纯 Python ncm 解密实现或 WASM 移植））；
   - 前端本地解密（WASM）+ 浏览器下载，后端零改动（隐私最优，性能受限）。
3. **链路设计要点**：`GET /api/download/{song_id}?format=mp3|flac` 流式响应 + `Content-Disposition`；批量下载（歌单/专辑）需任务队列 + 进度反馈（zip 打包）；VIP 音质权限与「可播放 ≠ 可下载」的降级策略。
4. **合规红线（先定死再开发）**：仅限用户**有权收听**的内容供个人离线使用；不做分享/分发；README 增加使用声明。分批下载（整单）是否开放需单独决策——建议默认关闭、设置中显式开启。
5. **UX**：单曲右键「下载」+ 详情页批量入口；格式/音质默认值进设置；大文件下载中断续传与否（建议 v1 不做）。
- 预估 5–8 人日（若 ncmdump 路线受阻需替代方案，另加 2–4 人日）。

> 版本规模：v0.1.7 预估 5–8 人日（设计细化后回填），v0.1.8 预估 5–8 人日（路线受阻另加 2–4 人日）。
