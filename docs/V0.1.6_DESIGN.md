基线见 `archived/V0.1.5_DESIGN.md`（多账号凭证库，已实现）与 `archived/V0.1.1_DESIGN.md` ~ `archived/V0.1.4_DESIGN.md`。

> 版本路线：v0.1.5 多账号凭证库（已完成）→ **v0.1.6 体验优化：交互快赢 + 性能 + 首页 + 自定义背景**（本版）→ v0.1.7 唱片墙展示 + 分享卡片（核心，延后）→ v0.1.8 下载与格式转换（核心，延后）。

## 1. 目标

1. **高频交互顺手**：左上角回首页、播放队列点空白收起、音量 UI 微调——改动小、感知强，最先落地。
2. **「我喜欢」/ 音乐库加载提速**：消除明显等待感，冷加载有可量化改善（目标见 §4.3）。
3. **首页成为像样的入口**：补齐模块、给出个人数据摘要与最近播放，但**不引入推荐流**（README 产品原则）。
4. **自定义背景图片**：本地图片 + 不透明度 / 模糊度 / 缩放 / 移动，可持久化、可一键关闭。

> 分享（反馈明确为**卡片式**、非链接、无二维码）与唱片墙展示合并至 v0.1.7，见 `V0.1.7_DESIGN.md`。

## 4. 方案对比与决策（按功能）

### 4.1 队列点击空白收起（#2）

| 候选 | 说明 | 结论 |
|------|------|------|
| a. 全屏半透明遮罩，点遮罩收起 | 判定简单、不会误触 | ❌ 首次点击被拦截，队列开着时无法直接操作页面，反而变慢 |
| **b. 面板外 `pointerdown` 即收起（决策）** | `document` 监听，命中在面板 ref 内则忽略；配合 `Esc` | ✅ 不拦截页面交互，抽屉式浮层的标准行为 |
| c. 仅当点击「页面空白处」（`e.target === 容器`）收起 | 最贴字面需求 | ❌ 命中判定随 DOM 嵌套脆弱，点到卡片/文字就不收起，行为不可预期 |

**决策：b。** 点击面板外**任意**位置（含左侧空白）收起队列；点击面板内不收起；`Esc` 同样收起。副作用（点歌曲行会顺带收起队列）为可接受的抽屉语义。右键菜单弹出的场景下，菜单点击不触发收起（命中判定排除 `ContextMenu` 根节点）。

### 4.2 音量 UI 微调（#3）

| 候选 | 说明 | 结论 |
|------|------|------|
| a. hover 展开式滑条（网易云式，默认只留图标） | 视觉省空间 | 备选记录：窄屏有价值，本版不做（展开动效 + 命中区复杂度不匹配「微调」诉求） |
| **b. 常驻滑条视觉统一 + 交互打磨（决策）** | 与 `ProgressBar` 共用滑轨/滑块视觉 token | ✅ 改动集中在一个组件，直击「微调空间」 |
| c. 弹出式音量面板 | 信息可扩展 | ❌ 过重 |

**决策：b**，具体微调项：

1. 自绘滑条与 `ProgressBar` 同款（同滑轨高度、滑块 hover 放大、accent 配色），替代原生 `range`；
2. 命中区从 `h-1` 提升到 `h-4`（视觉不变、好点好拖）；
3. 拖动 / 悬停显示百分比气泡；静音钮显示三态图标（静音 / 低 / 高），点击切静音并**记住静音前音量**（恢复准确）；
4. 悬停滚轮微调 ±5%（`preventDefault` 防页面滚动），键盘 `↑/↓` ±5%（聚焦时）；
5. 音量记忆沿用 v0.1.2 规则不变（`csplayer:prefs:volume`）。

### 4.3 性能：我喜欢 / 音乐库加载（#4）

先度量再动手（S0-1），候选按「收益 / 风险」排序：

| 候选 | 说明 | 结论 |
|------|------|------|
| a. 前端 SWR + 骨架屏 | 二次进入立即显示上次数据、后台刷新；首屏出骨架而非整页 Loading | ✅ 做（感知提升最大、零协议改动） |
| b. 后端上游并发 + 字段裁剪 | `library_service` 链路内串步改 `asyncio.gather`；响应只保留前端用到的字段 | ✅ 做 |
| c. GZip 中间件 | likes 千级曲目 JSON 可观 | ✅ 做（**排除 `/api/stream`**，避免二次压缩音频流） |
| d. 后端内存 TTL 缓存（likes/liked-ids） | 收益视上游耗时占比 | ⏸ 视 S0-1 结论决定；风险：`toggle` 红心后失效一致性，需失效钩子 |

**决策：a + b + c 进本版，d 挂起。** 量化目标（S0-1 记录基线后回填）：

- 二次进入 `/like`、`/library`：**缓存即时可见**（<100ms 出内容，后台静默刷新）；
- 冷加载：接口 P95 较基线**下降 ≥40%**，或首屏可交互 <1.5s（局域网部署），二者取先达标者。

**S0-1 基线与瓶颈结论（2026-09 回填）**：

1. **瓶颈归因**：冷加载延迟主体是**上游串行往返**——SDK 非线程安全，全部调用经单线程 executor + 锁串行进单一 worker 进程（`core/ncm_client.py`），任何「并发」都不缩短上游链路；`/like` 冷路径 = `user_playlist`×1 + `playlist_track_all`×⌈N/50⌉（另有前端 `/user/liked-ids` 的 `likelist`×1 与之抢锁）；`/library` = `user_playlist`×1 + `album_sublist`×⌈M/50⌉。响应体积次之（局域网不敏感、远程部署显著）；整页 Loading 导致的**感知慢**是体验上的最大项。
2. **体积基线（合成样本实测，1000 首 likes）**：旧载荷 270.2KB → gzip 后 73.3KB（3.7x）；字段裁剪后 263.4KB → gzip 70.7KB。albums（200 张）：35.8KB → 28.4KB（裁剪后）。
3. **往返基线（代码推导，确定性）**：`/like` 冷路径从 `2 + ⌈N/50⌉` 次（含与之抢锁的 likelist）→ `⌈N/50⌉` 次（`liked_playlist` 长缓存命中后，见 §12.1）；`/user/liked-ids` 在 likes 缓存命中时 0 次。
4. **判定**：d（新增 TTL 缓存）**不做**——现有 `TTLCache`（`user_likes` / `user_liked_ids` 60s + `_invalidate_like_cache` 失效钩子）已覆盖且读己之写一致（桩验证）→ **S2-4 关闭**。
5. **目标达成路径**：二次进入 <100ms 由 SWR 纯本地渲染达成；冷加载按「二者取先达标者」以**首屏可交互 <1.5s** 达成（骨架屏即时渲染、页面立即可交互），接口 P95 降幅受 SDK 串行约束（§12.1）以 perf 日志实测回填。

### 4.4 优化首页（#5）

| 候选 | 说明 | 结论 |
|------|------|------|
| a. 最小修补 | 只补「我的歌单」入口、统一模块文案 | 不够，反馈明确要求「优化」 |
| **b. 导航 + 个人数据摘要 + 最近播放（决策）** | 欢迎条（头像/昵称）+ 4 模块入口 + 概览数字 + 最近播放 50 条 | ✅ 全部来自个人数据与本地记录，符合「无推荐流」原则 |
| c. 门户化（新碟速递、排行榜推荐、每日推荐） | 信息丰富 | ❌ 直接违反 README「无广告、无推荐流」产品定位 |

**决策：b**。首页结构：

```text
首页
├─ 欢迎条：头像 + 昵称 + 一句副标题
├─ 概览：我喜欢 N 首 · 我的歌单 N 个 · 收藏专辑 N 张（复用现有接口，异步补数、不阻塞首屏）
├─ 模块入口 ×4：我喜欢 / 我的歌单（音乐库）/ 自听榜 / 唱片架（文案与侧栏统一）
└─ 最近播放：本地记录 50 条（点击续播，右键沿用歌曲右键菜单）
```

- 最近播放为**新的本地偏好** `csplayer:prefs:recentPlays`（新工具 `utils/recentPlays.ts`，与 `recentSearch.ts` 同风格）：歌曲**开始播放**时记录、同曲去重置顶、上限 50、可一键清空；**不上传、不跨设备**。
- 概览数字：`likesStore` 已有 tracks、`libraryApi.playlists/albums` 已有 total，**零后端改动**；懒加载失败则隐藏该数字，不影响进入。

### 4.5 自定义背景图片（#7）

| 维度 | 候选 | 结论 |
|------|------|------|
| 存储 | a. 压缩后 dataURL 存 localStorage（`csplayer:prefs:background` 独立 key） | ✅ 与既有偏好链路一致、实现最简；前置 canvas 压缩（最长边 ≤1920、JPEG q0.8、目标 ≤300KB），超限提示「图片过大」 |
| | b. IndexedDB 存原图 | 备选演进（多图轮播/原图需求出现时再迁），本版不引入新存储面 |
| | c. `URL.createObjectURL` 不持久化 | ❌ 刷新即失效，与「个性化设置」预期不符 |
| 内容层可见性 | a. 应用底色改半透明表面 token（`--surface-*` 带 alpha），开关控制 | ✅ **「背景启用」时**才切半透明，**默认关闭 = 现状实色，零回归** |
| | b. 全量改造 UI 为半透明 | ❌ 波及全部主题、回归面过大 |
| 移动交互 | 设置卡内预览框拖拽平移 + 双击复位 + 数值滑杆 | ✅ 不污染主界面交互 |

**决策：** 独立设置节「背景」（`SettingSection id="background"`，排「主题外观」之后），控制项：选择/移除图片、不透明度 0–100%（默认 40）、模糊 0–40px（默认 0）、缩放 100–300%（默认 100）、位置拖拽（x/y 持久化，双击复位）、开关「背景启用」。

- 渲染：`BackgroundLayer`（`fixed inset-0`，置于内容层之下），`<img>` 走 `transform: translate(x,y) scale(s)` + `filter: blur(px)` + `opacity`；平移缩放只动 transform，避免重排。
- 性能兜底（S4-3 验收）：模糊 ≥24px 时在低端机不应导致播放卡顿/滚动掉帧，超标则把大模糊改为**压缩阶段 canvas 预模糊**（运行时只做 ≤24px）。
- 持久化：与 `contextMenu` 相同的独立 key 模式（`csplayer:prefs:background`），不进 `PREFS_KEY` 主信封（避免大字段进 backup 轮换）；「恢复默认设置」与「清除本地数据」**都**清除该项（属偏好、非凭证）。
- 隐私：图片仅存本机浏览器，不上传后端（说明文案沿用 v0.1.2 风格写在设置卡上）。

## 6. 关键时序


## 8. 风险与合规（记录在案）

| 风险 | 说明 | 处理 |
|------|------|------|
| 分享卡片合规 | 卡片含封面/标题，可能被二次传播 | 只输出图片卡片、不含音频文件；细节在 v0.1.7 设计讨论时确定 |
| 背景图隐私 | 用户照片类图片入库 | 仅存浏览器 localStorage、不上传后端、设置卡明示、可一键移除 |
| localStorage 容量 | 背景图 dataURL 可能挤爆 5MB 配额 | 压缩到 ≤300KB；写入 try/catch 静默失败并提示「存储空间不足」；超限时引导换图（IndexedDB 演进见 §4.5） |
| blur 性能 | 大模糊值固定层重绘开销 | §4.5 预模糊兜底；验收含低端场景走查 |
| GZip 误伤流式 | 音频流二次压缩 | 中间件排除 `/api/stream` |
| SWR 数据陈旧 | 缓存先显 + 静默刷新存在短暂旧数据 | 红心等写操作后立即失效本地缓存；切账号（`dataVersion+1`）时清空缓存重拉 |

### 11.2 v0.1.8 下载与自动转换格式（核心，全栈主题版）

反馈「**下载并自动转换格式：使用库 [ncmdump](https://github.com/taurusxin/ncmdump)**」。独立成版理由：跨语言依赖集成 + 后端新链路 + 版权合规边界 + 大文件/转码 UX，是本批**技术不确定性最大**的需求。

**预研要点（S0 级调研建议提前至 v0.1.6 期间并行）**：

1. **场景澄清（先决问题）**：`ncmdump` 解的是网易云 `.ncm` 加密缓存；而 API 直链拿到的一般是普通 mp3/flac。需澄清目标场景：(a) 下载 API 直链音频 + 统一转码格式；(b) 解密用户自备 `.ncm` 文件；(c) 两者都要。**结论直接决定集成路线**。
2. **集成路线候选**：
   - 后端 Python 直连：下载流 → `ffmpeg` 转码（依赖本机 ffmpeg，启动时探测并提示）；
   - `ncmdump` 以 CLI/库形式集成（C++/C# 实现，Windows 向；需评估跨平台替代（纯 Python ncm 解密实现或 WASM 移植））；
   - 前端本地解密（WASM）+ 浏览器下载，后端零改动（隐私最优，性能受限）。
3. **链路设计要点**：`GET /api/download/{song_id}?format=mp3|flac` 流式响应 + `Content-Disposition`；批量下载（歌单/专辑）需任务队列 + 进度反馈（zip 打包）；VIP 音质权限与「可播放 ≠ 可下载」的降级策略。
4. **合规红线（先定死再开发）**：仅限用户**有权收听**的内容供个人离线使用；不做分享/分发；README 增加使用声明。分批下载（整单）是否开放需单独决策——建议默认关闭、设置中显式开启。
5. **UX**：单曲右键「下载」+ 详情页批量入口；格式/音质默认值进设置；大文件下载中断续传与否（建议 v1 不做）。
- 预估 5–8 人日（若 ncmdump 路线受阻需替代方案，另加 2–4 人日）。

> 版本规模：v0.1.7 预估 5–8 人日（设计细化后回填 `V0.1.7_DESIGN.md`），v0.1.8 预估 5–8 人日（路线受阻另加 2–4 人日）。

## 12. 实施补记（预留）

实施中的决策微调统一记录于此，**与上文冲突处以本节为准**（体例同 v0.1.5 §10）。

### 12.1 S2-1 实施微调：SDK 单线程串行约束下「减往返优先」

实测/代码确认：NCM SDK 非线程安全，全部上游调用经**单线程 executor + 锁**串行进单一 worker 进程（`core/ncm_client.py`）——`asyncio.gather` 只改变编排方式，**不缩短上游链路耗时**。因此 S2-1 的收益取向调整为（与上文冲突处以本节为准）：

1. **减往返优先**：`liked_playlist_id` 与 `user_playlists` 共用 `user:{uid}:playlists:raw` 上游缓存（两者本各自调一次 `user_playlist`）；`user_liked_ids` 在 likes 缓存命中时直接派生 ids；前端 `fetchIds` 在 tracks 已加载时短路（likesStore 单一数据源）。
2. **`liked_playlist` 长 TTL（24h）**：「我喜欢」歌单 pid 对账号不可变，长缓存消除重复冷路径上的 `user_playlist` 往返；`trackCount` 仅作分页编排 hint，滞后由 `_playlist_tracks`「末页满页续拉」自校正；like 变更后不失效该项（避免每次红心多打一次上游），只失效 `playlists:raw` / likes / liked_ids / 歌单缓存。
3. **gather 仍落地**（`_playlist_tracks` 按 hint 一次编排全部分页），当前收益为省去逐页 await 空隙，SDK 并发化后可零改动直接受益；缺 hint 时保留原串行循环（向后兼容、崩溃风险面不变，单页 50 条不动——历史上大响应会崩 QuickJS）。
4. `music_service` 无串步依赖链（song_url 的 v1 → 旧接口是**回退**而非并行候选，保持不变）。

### 12.2 字段裁剪明细（显式契约适配）

逐字段核对前端使用集后：`SongSummary` / `PlaylistBrief` 字段集已等于前端使用集（`map_song` 本就从上游大对象裁剪），无可裁项；实际裁剪：

- `/api/user/likes` 去掉 `ids`（与 `tracks[].id` 全量冗余，前端自 tracks 派生）：1000 首省 ~7KB raw；前端 `LikedSongs.ids` 改为可选（唯一使用方 `fetchTracks` 本就不用它）。
- `AlbumBrief` 去掉 `publishTime` / `size`（前端零消费方）：200 张省 ~7.4KB raw；`AlbumDetail.publishTime` 保留（详情页单对象，后续展示可用）。前端 `AlbumBrief` 类型同步移除（显式适配，tsc 全量校验通过）。

### 12.3 S2-3 SWR 范围：内存快照，未做 localStorage 快照

localStorage 快照为设计中的**可选项**，本版不做：① 多账号下需按 userId 隔离快照，否则切账号瞬间串数据（与 §8 风险表冲突面大）；② 红心变更后本地快照一致性需额外失效链路；③ 内存 SWR 已满足「二次进入 <100ms」（验收语境为应用内二次进入）。代价：整页刷新后首进入仍出骨架屏（但页面立即可交互，满足 §4.3 首屏目标）。后续如需跨刷新秒开，再按 userId 分键落 localStorage。

### 12.4 S2-4 挂起项关闭

见 §9 S2-4 结论：现有 `TTLCache` + `_invalidate_like_cache` 已覆盖需求语义，不新增代码。

### 12.5 S0-1 度量落地与目标判定

- 常驻 `PerfLogMiddleware`（`app/main.py`）：`perf <method> <path> <status> <ms> <KB> upstream=<n>次 <ms>`，覆盖全部 `/api/*`；体积为**压缩后实际写出字节**，upstream 为该请求内 SDK 调用次数与累计耗时（`core/ncm_client.py` contextvar 按请求归因），可直接区分「上游 / 串行 / 体积」。
- 基线数字（体积实测 + 往返推导）见 §4.3 回填；**接口 P95 前后对比需真实登录态**，开发环境无上游会话无法实测，验收时分别在改动前后环境各跑一轮（或仅凭 upstream 字段归因）回填。
- 目标判定：二次进入 <100ms ✓（SWR 纯本地渲染）；冷加载按 §4.3「二者取先达标者」以**首屏可交互 <1.5s** 达标（骨架屏即时渲染）；「P95 下降 ≥40%」受 §12.1 串行约束未作为达标依据。

### 12.7 附加（验收期新增）：后端日志脱敏，登录凭证只留在浏览器

凭证合法位置仅两处：浏览器 localStorage（v0.1.4 起）与后端**内存**会话（零落盘）。2026-09 审计发现真实泄漏面：**MusicLibrary SDK 原生层（QuickJS / engine.dll）直写 OS 文件句柄 1**（`[ROUTE] ... cookie: {"MUSIC_U": "...", ...}`），SDK 子进程继承 uvicorn 的 stdout，绕过 logging 将**整份 cookie 落进 `backend/uvicorn.log`**（实查 19 行含真实凭证）；此外异常文本（SDK 错误串、Pydantic 校验错误回显输入值）也有泄漏风险。

处理（新增 `app/core/logutil.py`）：

1. `redact()` 统一脱敏（敏感键值 → `[REDACTED]`，URL query 抹除；空值不误伤、不跨行）；`RedactingFormatter` 包装 `csplayer.*` 与 `uvicorn.*` 全部 handler（含异常栈文本）；
2. `ncm_worker` 入口 `install_worker_redaction()`：**fd 层**接管 stdout/stderr（dup 保留真实 fd → 管道替换 fd 1/2 → 泵线程按行脱敏转发）；**实施教训**：v1 仅包 `sys.stdout` 无效——噪声来自原生层直写 fd 1，验收实测仍泄漏，下沉到 fd 层后真实 SDK 端到端验证通过（`[ROUTE]` 行结构保留、cookie 全部 `[REDACTED]`）；
3. 缓存键用 `cred_fingerprint()`（sha256 前 16 位）替代 `MUSIC_U` 明文前缀（`get_me` 的 `user_profile:*` 键）；
4. **既有泄漏清理**：`backend/uvicorn.log` 已用同一 `redact()` 就地清洗（19 行凭证 → `[REDACTED]`）；该文件被 `*.log` 规则 gitignore，历史提交无泄漏（已核查全部分支）。

自测（桩脚本，不入库）：真实泄漏样本、键值对 / cookie 串 / URL query 各形态、幂等与不误伤（`cookie: {}`、perf 日志、空值键）、跨行结构保持、异常栈脱敏、fd 层原生直写/print/无换行尾块三形态拦截、真实 SDK worker 端到端（假凭证零残留）——全过。

### 12.8 S0-2 存储实验与压缩阶梯（§4.5 微调，与上文冲突以本节为准）

合成样本（1080p / 4K UI 截图 + 高频细节照片类）走「canvas 压缩 → dataURL」管线实测（临时脚本，不入库）：

| 样本 | q0.8/1920 | q0.7/1920 | q0.6/1920 | q0.5/1600 | q0.5/1280 |
|------|-----------|-----------|-----------|-----------|-----------|
| 1080p 截图 | 111KB | 99KB | 92KB | 65KB | 46KB |
| 4K 截图 | 107KB | 94KB | 86KB | 62KB | 43KB |
| 照片（4000×3000 级） | **462KB** | 325KB | 241KB | 108KB | 56KB |
| 照片·高细节 | **359KB** | 252KB | 182KB | 82KB | 45KB |

1. **固定 q0.8 不可行**：截图类（背景图主要用途）达标，但高频照片类超 300KB；**不升级 IndexedDB**（设计中的备选演进），改为**自适应降级阶梯**（`BackgroundSettings.LADDER`：q0.8→q0.7→q0.6 @1920 → q0.5@1600 → q0.5@1280），逐档重压至 ≤300KB，全部样本 ≤241KB；「图片过大，请换小图」仅在全部降档仍超限时出现（实际几乎不会）。与 §4.5「q0.8、超限提示」的差异以此为准。
2. **配额与失败行为**：300KB dataURL（ASCII）在 localStorage UTF-16 计量下 ≈ 600KB，5MB 配额下占比 ~12%，与偏好/队列快照共存安全；写入 try/catch 静默降级（内存态继续生效）+ 提示「存储空间不足」，应用不崩。
