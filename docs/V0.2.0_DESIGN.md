# V0.2.0 设计文档：后端 SDK 迁移（pymusiclibrary → NeteaseCloudMusicApi）

> 状态：**设计已批准（2026-10），方案 B**；排期在 v0.1.x（v0.1.8 样式 / v0.1.9 下载）完成之后启动。
> 相关文档：`BACKEND_ARCHITECTURE.md`（现架构）、`archived/DEBUG.md`（SDK 崩溃史与隔离决策）、`docker/README.md`（Docker 阻塞结论）、`ROADMAP.md`（版本路线）。

## 1. 背景与动机

现后端 SDK 为 `pymusiclibrary`（C + QuickJS 原生库，Windows-only），三个固有缺陷（详见 `BACKEND_ARCHITECTURE.md` §2.2 / `archived/DEBUG.md`）：

1. **原生崩溃毒化进程**——access violation 后堆已写坏，被迫整套子进程隔离（`ncm_worker.py` + Pipe RPC + 崩溃重试 + 熔断退避，约 280 行纯对抗性代码）；
2. **非线程安全**——上游调用强制串行（`max_workers=1` + Lock），分页 gather 只能伪并行；
3. **仅 Windows**——Linux 无原生库，Docker 部署计划因此回滚（`f757b62`，结论见 `docker/README.md`）。

目标 SDK：**NeteaseCloudMusicApi**（NCMA，纯 Node.js，377 个接口模块；`NCMA_Demo/` 已验证搜索 / 详情 / 播放 URL / 歌词 / 歌单链路可用）。

## 2. 收益与风险

### 收益

| # | 收益 | 说明 |
|---|---|---|
| 1 | 跨平台 | Linux / macOS 可用 → Docker 一键部署可照 `docker/README.md` 附录直接恢复 |
| 2 | 删除隔离机制 | `ncm_worker.py`、崩溃重试、熔断退避、fd 级 stdout 接管（`logutil.install_worker_redaction`）全部删除 |
| 3 | 解锁并发 | NCMA 函数为纯 async（axios），可并发调用；分页 gather 真并行（注意风控，加并发上限） |
| 4 | 解锁「最近播放」 | `record_recent_song` 登录态原生崩溃（v0.1.1 搁置）根因消失，云端版可重启评估 |
| 5 | 上游覆盖全 | 377 模块，与网易云接口同步更直接 |

### 风险

| # | 风险 | 缓解 |
|---|---|---|
| 1 | 上游维护性：binaryify 原仓库状态不稳，npm `NeteaseCloudMusicApi` 停在 4.32.0 | 小样本对比 `@neteasecloudmusicapienhanced/api@4.40.1`（更活跃）后定（待决 §8） |
| 2 | 新增常驻 Node 进程：部署 / 启动脚本 / 健康检查 | worker 由启动脚本拉起；`/api/health` 可选加探活 |
| 3 | 已验证调用点 22 个，需全量回归 | 回归清单见 §6 |

## 3. 方案对比与决策

| 方案 | 形态 | 改动量 | 优点 | 缺点 |
|---|---|---|---|---|
| A：sidecar HTTP | NCMA 起本地 HTTP 服务（A1 自带 server / A2 薄封装），`ncm_client.py` 改 httpx 调用 | 中 | curl 可调试、进程独立、业务层零改动 | 双进程 + 端口管理；**A1 有坑**：apicache 中间件缓存 key = `hostname+url+req.cookies`（仅 Cookie 头），凭证若走 query 传参，不同账号命中同一缓存 → **跨账号数据污染**；须走 Cookie 头或禁用该中间件 |
| **B：Node stdio worker（已选）** | 仿现有形状：~60 行 Node worker，JSON-lines over stdio 直调 NCMA 函数，替换 `ncm_worker.py` | 小 | 无端口 / 无 HTTP 开销 / 凭证不进 URL；`ncm_client.py` 进程管理与协议骨架保留，只删崩溃分类；架构图几乎不变 | 不可 curl 调试；worker 协议自研（远比现版简单） |
| C：后端整体迁 Node | services / session / cache / mapper / 限流 / 流代理全重写（约 2000 行 Python → TS） | 大（10+ 人日） | 单运行时、前后端同语言 | 与「切 SDK」不成比例；回归面全量。可作长期方向，本次不做 |

**决策（2026-10，已批准）：方案 B。** 无论 A/B，`ncm_call(fn_name, cookie, **kwargs) -> Response` 签名不变，services 层以下全部不动。

### 目标架构（方案 B）

```
FastAPI 主进程（业务、会话、缓存、限流、映射 —— 全部不动）
  └─ ncm_client（进程管理 + 超时；崩溃分类 / 熔断 / 串行锁删除，换 semaphore 限并发）
       └─ stdin/stdout JSON-lines（协议同现有 Pipe RPC，去掉 pickle）
            └─ ncm_worker.js 子进程（require('NeteaseCloudMusicApi') 函数直调，可丢弃）
                 └─ 网易云 API（axios，纯 JS，无原生库）
```

## 5. 工作分解（估算 3.5~5 人日）

### W1 SDK 接入层（core/，~1 人日）

- 新写 `ncm_worker.js`：stdin 收 `{fn, cookie, kwargs}` → `require('NeteaseCloudMusicApi')[fn]({ ...kwargs, cookie })` → stdout 回 `{ok, status, body, cookie}`。
- cookie dict ↔ 字符串序列化：`session.py` 补 dict→str（现只有 str→dict 的 `parse_cookie_str`）。
- **响应形状适配**：NCMA 返回 `{status, body, cookie: [Set-Cookie 数组]}`、无 `headers`；适配层把 `cookie` 数组包成现有 `Response.headers["Set-Cookie"]`，`auth_service` 三形态 Cookie 提取对齐。
- `ncm_client.py`：保留进程管理与超时（30s）；**删**崩溃分类（`_WorkerCrashed`/`_WorkerError`）、连续崩溃熔断、`max_workers=1` 串行锁；并发上限改 semaphore（建议 4，防上游风控）。
- `backend/` 新增 `package.json`（依赖 NCMA），或 vendor NCMA_Demo。

### W2 删除隔离机制（core/，~0.5 人日）

- 删 `ncm_worker.py`、`logutil.install_worker_redaction`（NCMA 不往 stdout 打凭证；`RedactingFormatter` 保留）。
- 确认 NCMA `main.js` 写 tmpdir 的 `anonymous_token` 文件无敏感内容（预期为空/匿名 token）。

### W3 接口迁移验证（services/，~1~1.5 人日）

- 按 §4 对照表逐点迁移；mappers 层预期零改动（上游 body 同源）——重点回归。
- 差异点：cloudsearch 替换通用 request、`noCookie` 实测、qrimg 验证。

### W4 部署与启动（~0.5~1 人日）

- `start.ps1` / `start.bat`：后端启动脚本先起 Node worker 宿主（或并入后端终端由脚本拉起）；首次 `npm install`。
- `requirements.txt` 去 `pymusiclibrary`；README「仅支持 Windows」改全平台 + Node 依赖说明。

### W5 机会项（迁移后解锁，不绑死本版）
